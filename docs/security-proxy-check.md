# Настоящие IP посетителей в журнале: удалённый сервер

Это настройка **журнала**, а не запрет входа с определённых IP. Не меняйте
SESSION_SECRET, пароли, ключи агентов и Google Drive.
Миграция БД для этой настройки не нужна.

## 1. Сначала проверить схему подключения

Выполните в **SSH-терминале**, не в SQL-редакторе:

```bash
sudo ss -lntp | grep -E ':(80|443|10000)\b'
sudo nginx -T 2>/dev/null | grep -n -E \
  'configuration file|server_name|location |proxy_pass|proxy_set_header (X-Forwarded-For|X-Real-IP)|real_ip_header|set_real_ip_from'
```

Команды ничего не меняют. Вторая показывает настройки всех сайтов:
для ERP нужно проверить соответствующий server/location целиком. Не присылайте
полный конфиг с секретами; для проверки нужны только адрес назначения API,
правила передачи IP и наличие промежуточного прокси/CDN.

Ожидаемая простая схема: посетитель → nginx → API на `127.0.0.1:10000`.
Если API слушает `0.0.0.0:10000` или `[::]:10000`, это ещё не доказывает
доступность из интернета, но требуется проверка межсетевого экрана.
У PostgreSQL также не должно быть ненужного публичного доступа.
Нельзя менять bind/firewall вслепую: сначала проверить зависимости.

## 2. Только после подтверждения простой схемы

Если **нет CDN/другого прокси перед nginx** и `$remote_addr` не переписывается
небезопасным `real_ip`-правилом, в location, который проксирует `/api/`,
nginx должен перезаписывать, а не копировать недоверенный заголовок:

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Real-IP $remote_addr;
```

Не добавляйте второй такой заголовок рядом с существующим: замените существующую
директиву в эффективном location. При CDN схема другая: доверяются только
подтверждённые сети этого CDN и проверенная цепочка адресов.

FastPanel может пересоздать конфиг. Перед изменением сохраните копию и используйте
предусмотренное панелью место для дополнительных директив. Существующий конфиг
целиком не заменять. После изменения:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

В конфигурации запуска PM2 сохраните переменную:

```text
SECURITY_TRUSTED_PROXY_CIDRS=127.0.0.1/32,::1/128
```

Эти значения подходят только для подтверждённого локального nginx.
Не использовать `0.0.0.0/0` или `::/0`.
Для применения к уже работающему процессу в SSH:

```bash
SECURITY_TRUSTED_PROXY_CIDRS='127.0.0.1/32,::1/128' \
  pm2 restart erp-davidov --update-env
pm2 save
```

Перезапуск кратковременно прерывает запросы. Не выводите `pm2 env` или `pm2 jlist`
в переписку: они могут содержать секреты.
Если деплой запускает PM2 заново из собственного конфига, переменная должна
оставаться и в этом конфиге, иначе следующее обновление сбросит настройку.

## 3. Проверить результат

С обычного внешнего браузера войдите в ERP. В новом событии входа должны быть:

- `peerIp`: локальный адрес nginx;
- `clientIp`: адрес внешнего клиента (или его VPN/провайдера), не `127.0.0.1`;
- `ipSource`: `trusted-proxy`.

Это влияет **только на новые события**. Старые адреса не восстановятся.
Для старых запросов можно искать совпадения по времени в сохранённых nginx-логах,
но одно совпадение IP не устанавливает личность человека.

Если результат неверный, уберите доверие к прокси (пустое значение переменной)
и перезапустите API с `--update-env`; не расширяйте доверенные сети наугад.

## 4. Закрыть прямой вход на порт API

Для подтверждённой схемы ERP nginx → `127.0.0.1:10000` задайте
`API_BIND_HOST=127.0.0.1` при перезапуске **после обновления и сборки API**.
Старая версия кода эту переменную не использует.
Без переменной остаётся прежний режим прослушивания Node, необходимый в Replit.
Непустое или пустое заданное значение, не являющееся IP-адресом, останавливает
запуск с явной ошибкой: ошибочная настройка не должна открыть порт всем.

Команды обновления удалённого сервера, в SSH под владельцем процесса PM2:

```bash
cd ~/www/erp.davidov-k.co.il &&
git pull --ff-only origin main &&
CI=true corepack pnpm install --frozen-lockfile &&
corepack pnpm --filter @workspace/api-server run build &&
PORT=10000 BASE_PATH=/ \
  corepack pnpm --filter @workspace/erp-platform run build &&
API_BIND_HOST=127.0.0.1 \
SECURITY_TRUSTED_PROXY_CIDRS='127.0.0.1/32' \
  pm2 restart erp-davidov --update-env &&
pm2 save &&
pm2 status
```

Проверка на сервере:

```bash
sudo ss -lntp | grep -E ':10000\b'
curl --max-time 10 -sS -o /dev/null -w 'HTTPS API: %{http_code}\n' \
  https://erp.davidov-k.co.il/api/settings
```

Ожидается только `127.0.0.1:10000` (не `*:10000`, не `[::]:10000`,
не `0.0.0.0:10000`) и HTTP `200` у публичных настроек через HTTPS.
Также проверьте вход в браузере. После этого нужна независимая проверка снаружи:
прямое TCP-соединение к публичным адресам сервера на порт 10000 не должно проходить.
Локальная проверка сама по себе не исключает другой процесс или перенаправление порта.

Эта настройка не меняет nginx и не ограничивает IP посетителей.
ИИ-агенты и вебхуки должны использовать публичный HTTPS URL `/api`,
не прямой порт 10000. Другие локальные процессы также сохраняют доступ к API;
это не замена авторизации или защиты учётной записи сервера.

## Клиентские изменения в том же обновлении

При `401` с текущим токеном приложение завершает сессию, очищает кеш и открывает
вход; поздний ответ от старого токена не закрывает новую сессию. Другие открытые
вкладки получают изменение через событие localStorage.
`403` не завершает сессию и не даёт пользователю дополнительных прав.
Автоматический запрос определений фильтров выполняется только с правом просмотра
исходной сущности; право на одну зеркальную страницу его не заменяет.

Для этих исправлений обновите и соберите frontend обычным способом. Пользователи
должны перезагрузить уже открытые вкладки, чтобы получить новый код.
SQL-миграций нет. Это уменьшает шум в журнале, но не заменяет ограничения
попыток входа, MFA и расследование подозрительных запросов.
