# Защита входящих интеграций

После обновления старые интеграции без разрешённых событий или с административными
ролями блокируются защитой. Это не удаляет настройки и историю: в списке и
мастерской отображаются причины. Переключатель активности не обходит блокировку.

## Как вернуть работу

1. Включите модуль, если требуется выполнять сценарии.
2. В настройках интеграции выберите роль без `superAdmin` и без административных
   разрешений. Оставьте только необходимые права на нужные сущности.
3. В мастерской задайте разрешённые события, по одному на строку.
   Например, `transferred_to_production`. Проверяется точное значение корневого
   поля `event` в JSON. Пустое значение, неизвестное событие и `*` запрещены.
4. Для создания пользователей выберите гостевую роль: без административных
   разрешений и без создания/изменения/удаления записей, включая зеркальные страницы.
   Название роли само по себе не даёт гарантии. Пользователь создаётся без пароля.
   Настройки поля `allowCreate` и разрешённых ролей также должны позволять создание.
5. Протестируйте пример и опубликуйте сценарий. Сохранённого черновика недостаточно.

При выполнении повторно проверяются модуль, активность технического пользователя,
его роли, сценарий и событие. Выключение модуля не только запрещает новые вебхуки:
ранее поставленные в очередь доставки также не должны выполнять бизнес-изменения.
Такие доставки остаются в истории с ошибкой; автоматического повтора после
исправления не предусмотрено. Перепроверяйте старую доставку перед ручным повтором.

Ключи ИИ-агентов не могут управлять интеграциями. Входящий JSON не назначает роль
или пароль. Найденный существующий пользователь не получает новые права или
пароль из сценария. Ошибка последующего шага откатывает создание пользователя.
В одной доставке допускается не более 500 выполнений шагов с учётом массивов.

## Границы защиты

Украденный действующий ключ всё ещё позволяет отправлять события, разрешённые
сценарием. Проверка поля `event` — ограничение сценария, а не доказательство
подлинности события. Отзывайте утёкшие ключи и проверяйте исходную систему.

Лимит 500 шагов — не ограничение частоты запросов или суточного числа новых
гостей. Такие квоты и подписывание запросов с временной меткой требуют
отдельной доработки. Полный доступ злоумышленника к серверу/БД не устраняется
проверками в коде ERP.

SQL-миграция для этого обновления не нужна: новые правила сохраняются внутри
существующего JSON сценария. Обновить нужно API и интерфейс.
