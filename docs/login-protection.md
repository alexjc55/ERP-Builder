# Защита входа от перебора

## Установка на удалённом сервере

Сначала выполните `scripts/migrate-login-throttle.sql` в SQL-редакторе базы ERP.
Затем соберите API и интерфейс и перезапустите API обычным способом.
Это новая обязательная таблица. Без неё вход безопасно отклоняется с HTTP 503.
Миграция не меняет пароли, роли, активность пользователей или их сессии.

Для сервера за nginx сохраните ранее настроенный SECURITY_TRUSTED_PROXY_CIDRS.
API должен оставаться доступным только через nginx (127.0.0.1).
Непроверенным заголовкам X-Forwarded-For система не доверяет.
Без настройки доверенного прокси все пользователи за ним могут разделять IP-лимит.

## Ограничения

Учитываются все запросы к входу, включая успешные и некорректные:

| Область | Максимум | Окно |
|---|---:|---:|
| Один IP, любые логины | 30 | 1 минута |
| IP + нормализованный логин | 8 | 15 минут |
| Один логин, любые IP | 40 | 15 минут |
| Весь API | 300 | 1 минута |

После достижения любого лимита: HTTP 429, Retry-After и отсчёт на кнопке входа.
Смена регистра/пробелов в логине не сбрасывает счётчик.
Отклонённые запросы не продлевают текущее окно. Действующие сессии продолжают работать.
Пользователь не отключается, его пароль не меняется. После окончания окна вход
доступен снова. При продолжающейся атаке следующее окно также может исчерпаться:
это не полная защита от отказа в обслуживании. Общие офисные сети разделяют IP-лимит.

Счётчики атомарны в PostgreSQL, общие для процессов API, переживают перезапуск.
Хранятся только числовые хеш-корзины, а не email, IP или пароли. Число строк
ограничено 196609; истёкшие корзины переиспользуются. Возможны редкие совпадения
корзин разных источников — в этом случае лимит общий (консервативный отказ).

Причины аудита: login_rate_limited и login_protection_unavailable.
Ошибки пароля и отсутствующий аккаунт возвращают одинаковое сообщение.
Для отсутствующего пароля выполняется контрольное bcrypt-сравнение, чтобы убрать
явный быстрый ответ для несуществующих аккаунтов; это не гарантия одинакового времени
при любых состояниях сервера.

Следующий уровень защиты — второй фактор для администраторов и проверка человека
при подозрительном потоке. Ограничение частоты не защитит от уже украденной сессии
или правильно введённого украденного пароля до достижения лимита.
